# digitalloco.github.io -- Claude Context

## Project Summary

The website for `digitalloco.com`: a short set of pages and a blog
about the digitalloco hobby project, served by GitHub Pages from
this repository in the `digitalloco` organisation. Claude writes and
maintains the pages and posts; Phil reviews them as diffs. The site
is currently a personal hobby project with nothing for sale, and
should say so wherever that could be in doubt. Say "currently":
the wording must not rule out software or boards being developed
or sold later (Phil, 2026-10-18).

## Project Phase

**Skeleton.** Astro (chosen 2026-10-18, replacing a day-old Hugo
skeleton) with our own minimal theme, a home page and an empty blog;
no real posts yet. Live at `digitalloco.github.io`; the custom
domain waits for DNS.

Astro was chosen because some pages will be data-driven reference
pages that readers are encouraged to bookmark, the first being a
cross-reference of decoder features, and those will eventually want
on-screen filtering.

## URLs are permanent

Readers are told to bookmark pages, so a published URL never
changes. Every URL is a directory with a trailing slash
(`trailingSlash: 'always'`).

- Posts: `/blog/YYYY/<folder-name>/`, year from the post's `date`.
  Renaming a post's folder or changing its year moves it -- do not.
- Reference pages: short, undated, permanent paths such as
  `/decoders/` and `/decoders/features/`. Choose the path with Phil
  before the first publish.
- Tags: `/tags/<tag-lower-hyphenated>/`. Feed: `/rss.xml`. Sitemap:
  `/sitemap-index.xml`, generated by `@astrojs/sitemap`.
- Archive `/blog/archive/`, search `/search/`, preview images
  `/og/site.png`, `/og/blog/<folder-name>.png` and
  `/og/docs/<section>/<page>.png`.
- Documentation: `/docs/`, `/docs/<section>/`,
  `/docs/<section>/<page>/`. First page: `/docs/railcom/standards/`.

## Content rules

- **Posts are plain Markdown.** No MDX and no components in posts
  without Phil's agreement; Markdown images and links only.
- **Front matter is YAML with these fields only:** `title`, `date`,
  `updated` (optional, set on a material revision; `date` never
  changes because the URL uses its year), `description`, `tags`,
  `draft`, as the schema enforces. A new
  field means a schema change, agreed first.
- **One folder per post**: `index.md` with its images beside it,
  referenced by relative path.
- **Drafts** (`draft: true`) show under `npm run dev` and never in a
  build.
- **Reference data lives in data files** under `src/data/`, each
  with a schema in `src/content.config.ts`; pages are generated from
  them. A table that readers rely on is never hand-written HTML.

## Documentation pages

Reference pages live under `/docs/<section>/<page>/`, separate from
the blog. Sections (RailCom now, DCC later) are listed in
`src/data/doc-sections.yaml`; a page is
`src/content/docs/<section>/<page>.md` with `title`, `description`,
`order` and a required `updated` (when the facts were last checked
against the sources). Adding a section means a new YAML entry and a
folder; the routes need no change.

- **Fact and opinion are kept apart.** Everything in the body is
  sourced from the documents themselves, with a public link. Our
  opinion goes in a blockquote that starts
  `**Commentary (YYYY-MM-DD):**`, rendered as a shaded box.
- **Check before stating.** Editions, dates and titles are read from
  the publisher's current file on the day, not from memory or from
  the private notes; the private repos may guide what to check but
  are never cited.
- Standards are named by publisher and number (RCN-217, S-9.3.2),
  and an RCN edition by its cover date.

## Theme and JavaScript

- Our own minimal theme, no third-party theme or CSS framework.
  Readable on a phone; light and dark from the browser, colours
  through `light-dark()` so the toggle works. **Prose pages carry
  no decoration**: no badges, colours or ornament.
- **Data tables may use colour and symbols where they make the
  table scannable** (agreed 2026-10-18 for the decoder index):
  tick, cross and question mark with tinted cells, grouped and
  abbreviated headers, sticky identity columns. Three conditions:
  the meaning is always in text too (a visually-hidden word or a
  `title`), so the table reads without colour, in a screen reader
  and when copied; the key is stated once on the page; and the
  styling lives in that table's component, not in `Base.astro`.
  Still no JavaScript: a native `popover` or `<details>` is fine,
  a script is not.
- **No client-side JavaScript by default.** Every page must work as
  plain HTML. Where a page earns interactivity (filtering a
  reference table), it is one small island on that page only, added
  after the plain-HTML version works, and agreed with Phil first.
- **Agreed exceptions (2026-10-18):** the light/dark toggle (two
  inline scripts in `Base.astro`; it only sets `color-scheme`, and
  the button stays hidden without JavaScript) and Pagefind search on
  `/search/` (with a `<noscript>` pointer to the archive). Only post
  `<article>`s are indexed (`data-pagefind-body`).
- Code highlighting is Shiki at build time with `light-dark()`
  colours, so it follows the toggle with no script.
- No new npm package without Phil's agreement. Versions are pinned
  exactly in `package.json` and `package-lock.json` is committed.

## Public content rules

This repository is public. Content follows the same rules as the
other public digitalloco repos:

- Cite only public URLs. Never link to, name the contents of, or
  quote from the private repositories.
- Proprietary decoder register meanings and defaults stay out. A
  decoder cross-reference may say what a decoder supports, not what
  a maker's own CVs mean; its data is curated for this site, not
  read from the bench notes.
- DCC-EX, RailCom and other parties' names appear only to say what
  a design works with or draws on, never as our product names.
- Bench results are reported as what one decoder did, not as what a
  standard means.

## Conventions

- British English spelling, no emojis
- Plain engineer's English; posts are prose, not notes
- Markdown linting required -- `npx markdownlint-cli2` on edited
  `.md` files before delivering
- Conventional commits: `feat:`, `fix:`, `docs:`, `chore:`
- **Never push without explicit permission for that push.** A push
  to `main` publishes the site. "Publish", "bring online" or "push"
  authorises one push, the one being discussed, and nothing after
  it: a later change, however small, waits for Phil to say push
  again. Committing locally is fine; pushing is not (Phil,
  2026-10-18, after pushes were made on earlier permission).
